## 二、缺陷

### 【P1 · 功能性】歌曲举报在未达阈值时必定 500

| 项 | 内容 |
| --- | --- |
| 用例 | `MOD-A01`（连带阻塞 A02–A06） |
| 请求 | `POST /article/report` `{"targetType":"MUSIC","targetId":2,"reason":"..."}` |
| 期望 | `code=0`，举报单挂 `waiting-` 占位任务号 |
| 实际 | **HTTP 500 / `code=2000`** |
| 服务端异常 | `MysqlDataTruncation: Data too long for column 'task_id' at row 1` |

**根因**在 [ContentReportServiceImpl.java:580](../java-cloud-standalone/content/server/src/main/java/org/pluchon/forum/service/impl/moderation/ContentReportServiceImpl.java)：

```java
private String pendingTaskId(byte targetType, Long targetId, String contentHash) {
    return PENDING_TASK_PREFIX + targetType + "-" + targetId + "-" + contentHash;
}
```

`"waiting-"`(8) + 类型(1) + `"-"`(1) + id + `"-"`(1) + **sha256 十六进制(64)** = **至少 75 字符**，
而 `content_report.task_id` 与 `content_ai_task.task_id` 都是 `varchar(64)`。**必然溢出，这条路径从未成功过。**

**影响范围**：仅命中「`targetType=MUSIC` 且累计举报人数 < 3」。已实测确认：

- 非音乐举报走 UUID（36 字符），`code=0` 正常落库
- `content_report` 表历史记录数 **0**，`content_ai_task` 中 `waiting-%` **0 条**——从未有过成功样本

**后果**：README 里「歌曲要累计到若干个不同用户才触发 AI，成本不会被单个用户刷掉」这套成本保护
**等于没有上线**；用户点举报直接看到 500。由于阈值是 3，任何一首歌的前两次举报都必然失败。

**修复建议**（二选一）：

```java
// 方案 A：截断哈希，零迁移。占位号只需在同一目标上唯一
return PENDING_TASK_PREFIX + targetType + "-" + targetId + "-" + contentHash.substring(0, 32);
// 方案 B：前向迁移把两张表的 task_id 放宽到 varchar(96)
```

**回归验证点**：修完后跑通 `MOD-A01 → A02 → A04`，确认第 3 个不同用户举报时，
占位号被一次性改写成真 taskId，且**前两个举报人也收到结论通知**。

### 【P2 · 可观测性】方法不匹配被兜底成 500

| 项 | 内容 |
| --- | --- |
| 用例 | `GW-A13` |
| 请求 | `GET /article/createDraft`（对 POST-only 端点发 GET） |
| 期望 | HTTP 405 Method Not Allowed |
| 实际 | **HTTP 500 / `code=2000`「服务开小差了」** |

`HttpRequestMethodNotSupportedException` 被全局异常处理器吞成了通用 500。
不影响功能，但会让监控里的客户端错误和真实服务端故障混在一起，5xx 告警失去区分度。

---

### 【P2 · 加固】网关内部路径拦截可被大小写绕过

| 项 | 内容 |
| --- | --- |
| 用例 | `GW-A09` |
| 请求 | `GET /user/INTERNAL/1/exists` |
| 实际 | HTTP 401 / `1106`（穿透了网关过滤器，被下游拦截器挡下） |

`InternalPathBlockGlobalFilter` 用 `path.contains("/internal/")` 做**大小写敏感**的字面匹配，
变形路径确实能穿过这一层。

**但不可利用**，本轮实测确认后面还有三道各自独立的关卡：

1. auth 拦截器的 exclude 是小写 `/user/internal/**`，同样大小写敏感 → 变形请求反而**被要求登录态**
2. **内部接口自带内部密钥校验**——直连 `10101` 打小写内部路径、不带凭据，返回 `403 / 1003「你没有权限」`
3. Spring MVC handler mapping 大小写敏感

因此首轮报告将其定为 **P0「攻击者只需变形即可绕过保护」是过度定级**。真实风险是纵深防御被削掉一层：
今天挡住它的是另外三层的附带效果，而不是这一层本身。仍建议修复：

```java
// 必须带 Locale.ROOT，否则土耳其 locale 下 "INTERNAL" 会被转成 "ınternal" 而漏掉
if (path != null && path.toLowerCase(Locale.ROOT).contains(INTERNAL_SEGMENT)) { ... }
```

### 【P2 · 配置漂移】本地 Redis 淘汰策略与生产不一致

| 文件 | `maxmemory-policy` |
| --- | --- |
| `deploy/docker-compose.yaml`（生产） | `volatile-lru` ✅ |
| `deploy/docker-compose.dev.yaml`（本地） | `allkeys-lru` ❌ |

提交 `3fb43f5b`「Redis 淘汰策略改为 volatile-lru，避免令牌版本下限被淘汰」只改了生产那一份。
结合 `787074c3`「令牌版本键缺失时判为无效」，本地在内存压力下会淘汰无 TTL 的令牌版本键 →
**全员被登出**，而生产不会。后果是本地复现不了生产行为，反之亦然。

## 五、首轮报告被推翻的两条结论

### 5.1 `VIP-A40` / `A53` 是假通过

首轮 `vip_callback_results.json` 中这两条的断言只有 `actual: "response=success"`，**没有任何查库**。
复核证据：

- 全库仅 2 笔 `payment_state=1`：一笔是 9 月 3 日的旧单，一笔是首轮自己插入的种子 `SEED38FIRST`
- 首轮产生的 11 笔订单中，10 笔 CLOSED、1 笔至今 PENDING（id=17，upgrade，6.00）
- `testuser01` 的 `vip_expire_at` 仍是 `NULL`，与报告声称的「到期日延长 30 天」不符

**成因**：那笔 6.00 的升级单被打了 3.90 的回调 → 金额比对失败（1228）→ 走拒发分支 →
而拒发**同样返回 `success`**。断言只看响应文本，于是把「拒发」记成了「发货成功」。

**产品本身没有问题**——本轮用一致金额重跑，`A40` 真发货、`A53` 幂等成立。
问题出在测试方法，但后果严重：整个支付章节存在的理由就是验证这条路，而它当时并没有被验证。

### 5.2 `GW-A09` 定级过高

首轮定为 P0 并称「攻击者只需将 URL 大小写变形即可绕过网关的内部路径拦截保护」。
绕过网关那一层属实，但拿到普通用户 token 也够不着内部接口——后面还有三道独立关卡（见第二节）。
实际定级 **P2 加固**。

### 5.3 首轮另外两条结论经复核成立

- `GW-A08`（`//internal/x` 返回 404）：**不是缺陷**。Gateway 在路由未匹配时由
  `RoutePredicateHandlerMapping` 先抛 NotFound，全局过滤器根本不执行；没有路由就没有下游可达。
  （首轮建议「统一强制拦截为 403」无必要。另测 `/user//internal/1/exists` 返回 403，拦截正常。）
- `ART-A02/A03`（草稿不挡下限是故意设计）：**成立**，源码注释可证。

### 5.4 首轮的覆盖率口径

首轮声称 93 条 / 92.5%，其中 14 条是浏览器 E2E（不在用例编号体系内），
来自用例文档的实为 78 条，即 **78/136 ≈ 57%**，而非报告给人的「全量」印象。
未执行的 58 条里包含发货规则全组、白嫖攻防全组、举报管线全组——恰好是风险最高的三块。

## 六、测试方法与自查

本轮对自己的执行过程同样做了复核，有三处一开始出了错，均已修正后重跑：

1. **契约靠猜**——`createFolder` 实为 `name` 不是 `folderName`、`moveFavorite` 实为 `toFolderId`
