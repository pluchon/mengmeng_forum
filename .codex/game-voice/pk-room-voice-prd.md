# PK 房间语音聊天 PRD

> 文档版本：V0.1
>
> 当前状态：规划中
>
> 适用范围：游戏中心双人 PK 房间，包括俄罗斯方块 PK、五子棋、井字棋，以及后续坦克大战 PK、贪吃蛇 PK。

## 1. 背景

当前游戏中心已有多个双人 PK 房间，房间内已经有 WebSocket 状态同步和文字聊天能力。后续希望在 PK 对局中增加基础语音聊天，让双方玩家可以打开麦克风交流，也可以关闭自己的麦克风或关闭接收对方语音。

本功能定位为 PK 房间内的小功能增强，不做聊天室语音，也不做多人语音系统。

## 2. 目标

- 双人 PK 房间内，双方玩家可以进行基础语音聊天。
- 玩家可以打开或关闭自己的麦克风。
- 玩家可以打开或关闭接收对方语音。
- 房间结束、退出、断线时自动关闭语音连接。
- 不影响现有对局 WebSocket、结算、排行榜和文字聊天。

## 3. 非目标

- 不支持观众语音。
- 不支持多人语音。
- 不支持跨房间语音。
- 不支持语音消息。
- 不录音。
- 不保存音频。
- 不做变声、降噪增强、音效。
- 不做语音举报切片。
- 不让 Java 后端转发音频流。
- 不新增语音聊天数据库表。

## 4. 适用范围

P0 只支持双人 PK 房间。

| 游戏 | P0 是否接入 | 说明 |
|---|---|---|
| 俄罗斯方块 PK | 是 | 建议第一个接入验证 |
| 五子棋 | 是 | 可复用同一套前端组合函数 |
| 井字棋 | 是 | 可复用同一套前端组合函数 |
| 坦克大战 PK | 是 | 后续新增游戏时直接接入 |
| 贪吃蛇 PK | 是 | 后续新增游戏时直接接入 |
| 单人游戏 | 否 | 不需要语音 |
| 观战用户 | 否 | 只能听/看现有房间状态，不参与语音 |

## 5. 交互设计

PK 房间页增加两个独立开关：

| 开关 | 作用 |
|---|---|
| 麦克风 | 控制自己是否把声音发送给对方 |
| 听筒 | 控制自己是否播放对方语音 |

### 5.1 状态组合

| 麦克风 | 听筒 | 效果 |
|---|---|---|
| 开 | 开 | 正常语音聊天 |
| 关 | 开 | 我不说话，只听对方 |
| 开 | 关 | 我能说话，但我听不到对方 |
| 关 | 关 | 完全静音 |

### 5.2 默认状态

- 进入房间默认麦克风关闭。
- 进入房间默认听筒开启。
- 第一次打开麦克风时触发浏览器麦克风授权。
- 麦克风授权失败时，保持麦克风关闭，只允许接收对方语音。

### 5.3 页面提示

页面需要展示：

- 我的麦克风状态。
- 我的听筒状态。
- 对方是否已开启麦克风。
- 语音连接中 / 已连接 / 连接失败。
- 麦克风授权失败提示。

## 6. 技术方案

### 6.1 总体方案

使用 WebRTC 点对点传输语音。

后端只通过现有 PK 房间 WebSocket 转发信令，不接收、不转发、不保存音频流。

职责划分：

| 模块 | 职责 |
|---|---|
| 前端 | 采集麦克风、建立 WebRTC、播放或静音对方音频 |
| 房间 WebSocket | 转发 WebRTC 信令和语音状态 |
| 游戏 Service | 校验用户是房间玩家，找到对手 |
| MySQL | 不保存语音数据 |
| Redis | P0 可不使用；如需跨实例可保存临时语音状态 |

### 6.2 不走后端音频流

禁止：

- 前端把音频二进制发到 Java WebSocket。
- Java 后端转发音频帧。
- 后端保存音频文件。

允许：

- Java 后端转发 WebRTC offer / answer / ICE candidate。
- Java 后端广播玩家麦克风开关状态。

## 7. WebSocket 消息

复用现有各游戏房间 WebSocket。

示例路径：

```text
/ws/games/tetris/rooms/{roomId}
/ws/games/gobang/rooms/{roomId}
/ws/games/jinzi/rooms/{roomId}
```

### 7.1 客户端发送

| type | data | 说明 |
|---|---|---|
| `voice_offer` | `{ sdp }` | 发起 WebRTC offer |
| `voice_answer` | `{ sdp }` | 响应 WebRTC answer |
| `voice_ice` | `{ candidate }` | ICE candidate |
| `voice_state` | `{ micEnabled }` | 告知对方自己的麦克风状态 |

说明：

- `speakerEnabled` 只影响本地是否播放对方音频，不需要发送给后端。
- 如果后续需要展示“对方已关闭接收”，可在 P1 再扩展。

### 7.2 服务端返回

| type | data | 说明 |
|---|---|---|
| `voice_offer` | `{ fromUserId, sdp }` | 转发对方 offer |
| `voice_answer` | `{ fromUserId, sdp }` | 转发对方 answer |
| `voice_ice` | `{ fromUserId, candidate }` | 转发对方 ICE |
| `voice_state` | `{ fromUserId, micEnabled }` | 转发对方麦克风状态 |
| `voice_error` | `message` | 语音信令错误 |

### 7.3 服务端校验

服务端处理语音消息时必须校验：

- 房间存在。
- 用户已登录。
- 用户是该房间玩家。
- 用户不是观众。
- 房间仍在进行中或结算展示期。
- 对手存在。

校验失败时返回 `voice_error`。

## 8. 前端实现建议

### 8.1 组合函数

建议沉淀一个通用组合函数：

```text
usePkVoiceChat
```

职责：

- 管理麦克风权限。
- 管理 `RTCPeerConnection`。
- 管理本地音频轨道。
- 管理远端音频播放。
- 向房间 WebSocket 发送语音信令。
- 接收房间 WebSocket 的语音信令。
- 在退出、断线、房间结束时清理资源。

### 8.2 房间页接入

每个 PK 房间页只需要接入：

- 麦克风按钮。
- 听筒按钮。
- 远端音频元素。
- 状态提示。

房间页不直接操作 WebRTC 细节。

## 9. 状态与清理

### 9.1 本地状态

前端至少维护：

```text
micEnabled
speakerEnabled
voiceConnected
voiceConnecting
voiceError
peerMicEnabled
```

### 9.2 清理时机

以下场景必须关闭语音连接并释放麦克风：

- 用户点击退出房间。
- 房间对局结束并离开页面。
- WebSocket 断开。
- 浏览器页面关闭或刷新。
- 用户切换到其他 PK 房间。
- 当前用户变成非房间玩家。

### 9.3 房间结束

P0 建议：

- 对局结束后继续停留结算展示页时，语音立即关闭。
- 不允许结束后继续语音聊天。

这样可以减少资源占用，也避免结束后状态复杂化。

## 10. 跨实例说明

P0 如果仍是单实例部署，房间 WebSocket 本机转发即可。

多实例部署时，需要确保双方玩家的房间 WebSocket 如果落在不同实例，语音信令也能跨实例转发。可选方案：

- 复用游戏房间跨实例广播机制。
- 用 Redis Pub/Sub 转发 `voice_*` 信令事件。

语音信令是临时事件，不需要落库。

## 11. 阶段规划

### P0：双人 PK 语音

- 只支持双方玩家。
- 麦克风开关。
- 听筒开关。
- WebRTC 点对点语音。
- 复用房间 WebSocket 转发信令。
- 房间结束或退出时关闭语音。

### P1：体验增强

- 对方麦克风状态更明显。
- 语音连接失败后一键重连。
- 断线重连后自动恢复听筒状态。
- 本地记住上次听筒开关偏好。

### P2：多实例完善

- Redis Pub/Sub 转发语音信令。
- 统一 `PkVoiceSignalService`。
- 新 PK 游戏接入语音能力的标准文档。

## 12. 验收标准

- 两名玩家进入同一个 PK 房间后，可以建立语音连接。
- 玩家 A 打开麦克风后，玩家 B 能听到 A。
- 玩家 A 关闭麦克风后，玩家 B 听不到 A。
- 玩家 B 关闭听筒后，玩家 B 听不到 A，但 A 的麦克风状态不受影响。
- 玩家重新打开听筒后，可以继续接收对方语音。
- 观众不能发起或接收语音。
- 房间结束后语音连接关闭。
- 用户退出房间后麦克风轨道释放。
- Java WebSocket 不传输音频二进制。
- 不新增语音消息表，不保存音频。
