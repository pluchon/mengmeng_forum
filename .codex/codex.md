# 项目长期开发规范

> 本文件是项目长期约束清单，属于不可随意突破的开发底线。
>
> 每次开始需求分析、设计、编码、修复或评审前，必须先阅读本文件，再阅读当前阶段的需求文档。

## 1. 需求与范围纪律

- 当前阶段需求文档是实现范围基线，禁止自行增加未确认的业务流程、表、字段、状态、角色或接口。
- 实现优先级遵守当前阶段文档中的 `P0 -> P1 -> P2`；不得为了增强项影响核心功能交付。
- 修改已有功能时必须保持历史数据和既有核心流程兼容，除非需求明确要求迁移或废弃。
- 当前阶段明确不做的功能不得偷偷混入实现。
- 需求文档之间发生冲突时：
  1. 优先遵守当前阶段明确指定的主设计文档。
  2. 其次遵守更具体、更严格的约束。
  3. 无法判断且会影响数据模型、权限或业务流程时，先向用户确认。
- 不得只完成表面页面或接口；需求中声明的权限、事务、日志、并发、测试和验收条件都属于功能的一部分。

## 2. 代码可读性强制规范

- 禁止将多个 `import`、字段、语句、方法、HTML 标签或 CSS 规则压缩在同一行。
- 每行只表达一个清晰操作。
- 复杂条件、链式调用和长参数必须合理换行。
- 禁止为了减少文件行数牺牲代码可读性。
- Java 类型统一在文件顶部使用 `import`，业务代码中禁止散落 `java.util.xxx` 等全限定类名。
- Java 数据库实体类及字段必须使用中文注释说明含义。
- Java 重要类、重要方法和关键业务分支必须使用中文注释说明业务原因、权限边界、事务边界和并发约束。
- 注释用于解释原因和约束，不写重复代码含义的无效注释。
- Java 注释风格统一遵守以下规则：
  - **类注释**：使用单行 `// 中文说明`，紧贴类声明上方；不使用 Javadoc `/** */`。
  - **字段 / 属性注释**：使用单行 `// 中文说明`，紧贴字段声明上方；不使用 Javadoc `/** */`。
  - **Controller 方法注释**：使用块注释 `/** 中文说明 */`，一句话说明接口用途。
  - **ServiceImpl、Mapper 等非 Controller 方法**：需要注释时使用单行 `//` 或块注释均可，视复杂度而定。
- 每个 DTO、VO 和 Entity 必须是独立的顶层 Java 文件，禁止在一个文件中用静态内部类聚合多个 DTO 或 VO。

## 3. Java 后端分层底线

- 后端调用链必须严格遵守：

```text
Controller -> Service -> Mapper
```

- 禁止 Controller 直接依赖 Mapper。
- Controller 只能负责接口注解、接收参数、调用 Service 和包装 `ApiResponse`。
- Controller 禁止编写业务逻辑、数据库逻辑、事务逻辑、审计逻辑、权限逻辑或实体组装逻辑。
- `service.interfaces` 只声明业务接口。
- `service.impl` 只放同名实现类，格式为 `XxxServiceImpl implements XxxService`。
- ServiceImpl 负责业务流程、资源归属校验、权限校验、状态校验、事务和必要的缓存操作。
- Spring 管理的 Controller、Service、Component、Configuration、Filter 等类，依赖注入统一使用字段 `@Autowired`。
- 基础 CRUD、分页、逻辑删除和时间填充优先使用 MyBatis-Plus。
- MyBatis-Plus 条件构造只允许使用 Lambda 系列 API，例如 `LambdaQueryWrapper`、`LambdaUpdateWrapper`、`Wrappers.lambdaQuery()` 和 `Wrappers.lambdaUpdate()`。
- 禁止使用依赖字符串列名的 `QueryWrapper`、`UpdateWrapper`、`Wrapper.apply()`、`last()` 拼接 SQL 等写法；确需手写 SQL 时必须放在 Mapper XML 或注解 SQL 中，并说明原因和参数安全边界。
- MyBatis-Plus 查询、更新、删除条件必须使用实体 getter 方法引用，例如 `User::getId`，禁止散落 `"id"`、`"user_name"` 等字符串字段名。
- 状态条件更新、并发竞争、资源状态联动等需要原子判断的场景使用明确的条件更新或手写 SQL。
- 所有业务状态变化必须通过明确的 Service 方法完成，禁止使用普通 CRUD 接口直接修改状态。

## 4. DTO、VO、Entity 与转换规范

- 所有请求体必须使用独立 DTO。
- 禁止使用 `Map<String, Object>`、`Map<String, String>` 等 Map 直接接收业务请求。
- 所有接口响应必须使用 VO 或 `PageResult<VO>`。
- 禁止 Controller 直接返回数据库 Entity。
- DTO 只表达请求参数。
- VO 只表达前端需要的响应字段和中文字段说明。
- 密码摘要、`securityStamp` 等敏感字段禁止出现在 VO。
- VO 内禁止编写 `from`、`toVO` 等实体转换方法。
- Entity 到 VO 的转换统一放在 `converter` 包，使用可直接维护的手写静态方法。
- 禁止引入 MapStruct 等编译期自动生成转换实现。
- ServiceImpl 必须直接调用 converter 静态方法，禁止将 converter 注册为 Spring Bean 或注入。
- ServiceImpl 禁止编写业务载荷、缓存载荷、DTO 或 VO 内部类；必须抽取为独立 Java 文件并补充中文注释。

## 5. 数据库与数据安全规范

- 全部数据库主键统一使用 MySQL `BIGINT AUTO_INCREMENT`。
- 禁止雪花 ID、`assign_id` 和应用层手动生成数据库主键。
- 新增业务表默认包含：

```text
create_time
update_time
delete_state
```

- `delete_state`：`0` 表示正常，`1` 表示已删除。
- 业务数据默认使用逻辑删除，普通查询必须排除已逻辑删除数据。
- 业务关闭、冻结、归档等状态必须使用业务状态表达，禁止用逻辑删除代替。
- 已被历史业务引用的数据不得物理删除。
- 操作日志、安全日志、状态流转日志等关键历史记录原则上只允许新增。
- 关键字段必须建立必要的唯一约束和查询索引，不能只依赖应用层校验。
- 唯一字段入库前必须标准化；手机号、邮箱、账号名等全系统唯一规则必须同时由业务校验和数据库约束保护。
- Flyway 迁移只能向前演进，不得随意修改已投入使用的历史迁移文件。
- 生产环境不得初始化默认管理员密码或开发演示账号。

## 6. 权限与安全边界

- 后端是最终安全边界，前端权限仅用于改善交互体验。
- 禁止信任前端传入的用户 ID、角色、资源归属或业务状态。
- Service 必须从当前认证上下文获取用户身份，并校验角色、资源归属、账号状态和具体操作权限。
- 数据库是账号状态、角色和权限的事实来源。
- 未认证返回 401，无权限返回 403。
- 普通用户只能查看和操作需求明确允许的资源。
- 高权限用户不能绕过角色边界创建、提升或修改同级及更高权限账号，除非需求明确允许。
- 停用、封禁、冻结或未激活账号必须遵守需求中的登录和业务限制。
- 上传、下载、查看或删除附件前，必须校验当前用户对关联业务资源的权限。
- 二维码、导出文件、接口响应和日志不得泄露不必要的敏感信息。

## 7. 认证、票据与会话规范

- 行为验证码、图形验证码、短信验证码和业务票据职责必须清晰，禁止混用。
- 验证码和业务票据必须绑定业务场景、目标地址或目标账号，禁止跨场景使用。
- 一次性票据必须原子消费，防止并发重复使用。
- 激活、恢复、换绑、重置等流程采用“先占用票据，事务成功后删除”的规则。
- 密码、联系方式、角色或账号状态变化后，必须更新会话安全标记并清除该账号全部会话。
- 清除缓存会话和删除票据应在数据库事务成功后执行。
- 日志禁止记录明文密码、验证码、JWT、业务票据、完整手机号和完整邮箱。
- 登录、敏感资料变更和权限变更等安全操作必须记录安全日志或操作日志。

## 8. 事务、并发与幂等规范

- ServiceImpl 中所有事务方法必须显式使用：

```java
@Transactional(rollbackFor = Exception.class)
```

- 数据库事务内只处理必须保持一致的数据库数据。
- 缓存清理、短信、邮件、SSE 和其他外部系统调用原则上在数据库事务成功后执行。
- 短信、邮件、SSE 等外部通知失败不得回滚核心业务事务，只记录失败日志或执行后续补偿。
- 状态更新、业务记录、流转日志、系统评论和站内通知等需求声明需一致的数据，必须处于同一数据库事务。
- 核心状态变更必须校验当前状态、版本号和操作权限。
- 编辑、提交、审批、分配和关键状态变化必须防止并发覆盖。
- 分配、确认或领取类操作必须重新校验操作者账号状态、资源关系、目标状态和版本。
- 提交、回调、自动任务和其他可能重复触发的入口必须具备幂等性。
- 定时任务必须防止多实例重复执行；单条失败不能中断整批任务。
- 删除数据或外部文件前必须再次确认没有任何有效业务引用。

## 9. 业务状态与流程底线

- 所有核心业务流程必须先定义状态机、允许操作、角色边界和失败分支，再进入编码。
- 状态编码必须稳定、可读、可追踪；禁止用魔法数字或页面文案直接驱动业务判断。
- 状态流转只能通过明确的业务方法完成，禁止绕过状态机直接修改数据库字段。
- 关闭、驳回、退回、撤销、删除、归档、审批等关键操作必须按需求填写原因或说明，并生成必要日志、评论或通知。
- 选择 `OTHER` 等兜底原因时，补充说明必须填写。
- 历史记录、快照、评论、通知和日志不得因当前资料变更而失真。
- 停用、冻结、归档或删除的配置、分类、字典、资源不能用于新业务，但历史数据必须正常展示。
- 自动状态联动不得覆盖人工设置的更高优先级状态。
- 同一资源存在未结束流程时，禁止错误恢复、重复分配或重复关闭。
- 管理员手动修正关键状态时，必须记录修正前状态、修正后状态、原因和操作者。

## 10. 日志与审计规范

- 关键业务操作必须记录操作人、操作时间、目标资源和操作结果。
- 登录成功与失败、密码和联系方式变化、用户状态与角色变化必须记录安全日志。
- 业务状态变化必须记录流转日志。
- 管理员特殊处理、导入、导出、删除和状态修正必须记录操作日志。
- 日志中的手机号和邮箱必须脱敏。
- 禁止在日志中记录密码、验证码、JWT、业务票据和其他认证秘密。
- 日志内容应能支持问题追踪，但不得泄露敏感数据。

## 11. Vue 前端强制规范

- Vue 文件只保留 `<template>` 与外部资源声明，禁止内嵌 JavaScript 和 CSS。
- 每个 Vue 文件必须使用同目录同名 `.js` 文件承载脚本。
- 存在私有样式时，使用同目录同名 `.scss` 文件；没有私有样式时不创建空 `.scss`。
- Vue 文件通过以下方式引用资源：

```html
<script setup src="./同名文件.js"></script>
<style scoped lang="scss" src="./同名文件.scss"></style>
```

- 必须保留 Vite 前置转换插件，在 Vue 编译前读取并注入同名脚本。
- 禁止移除转换插件后继续使用 `<script setup src>`。
- 页面禁止直接调用 Axios，统一通过 `src/api` 封装。
- 页面禁止直接修改 Store 内部状态。
- 业务状态统一使用枚举映射或共享组件，禁止在页面散落状态数字和重复映射。
- 前端路由、按钮和页面可见性按角色控制，但后端仍必须再次鉴权。
- 关闭、驳回、退回、撤销、删除等关键操作必须二次确认。
- 提交期间禁用重复操作按钮，但后端仍必须负责幂等和并发控制。
- 异步页面必须正确处理加载、空数据、错误和无权限状态。

## 12. Python 服务开发规范

- Python 代码必须按职责划分模块；新增能力必须先判断属于路由、客户端、业务编排、工具、存储、任务还是配置，禁止把不同职责混写在同一个模块。
- Flask 路由只负责鉴权、参数读取、输入校验、调用业务函数和包装 JSON 响应；禁止在路由函数中堆叠大段提示词拼接、外部服务协议、检索细节或后台任务逻辑。
- 新增接口必须遵守统一 API 版本和响应结构，错误状态必须返回匹配的 HTTP 状态码。
- Python 模块必须使用 `from __future__ import annotations`，类型标注使用内置泛型 `list[str]`、`dict[str, Any]`，禁止新增无必要的 `typing.List`、`typing.Dict` 写法。
- 函数参数和返回值必须补充类型标注；对外部接口、客户端和复杂工具函数必须明确返回结构，禁止返回含义不清的裸 `dict` 后再在调用方猜字段。
- 注释和 docstring 使用中文说明业务原因、边界和失败策略；禁止写重复代码含义的空注释。
- 单个函数只做一层清晰职责；超过一屏、包含多段校验、转换、远程调用或兜底逻辑时，必须拆分为私有辅助函数。
- 禁止在业务代码中散落读取 `os.environ` 或硬编码配置；配置必须集中读取、集中定义默认值和环境变量覆盖规则。
- 密钥、令牌、内部调用 key、数据库密码和对象存储凭证只能来自配置或环境变量；禁止写入代码、测试样例、日志或普通响应。
- 外部 HTTP 调用统一放在客户端模块，必须设置明确 `timeout`，必须处理非 2xx 响应，日志中只记录状态码和脱敏后的摘要。
- 调用大模型、地图、搜索、对象存储、转码、图片生成等外部服务时，必须限制输入长度、文件大小、返回摘要长度和重试范围，避免无界 token、内存、网络和费用消耗。
- 路由层禁止直接调用 `requests`、Redis、RabbitMQ、Postgres、对象存储 SDK 或其他基础设施 SDK；必须通过已封装的客户端、存储层或任务层完成。
- Redis key、消息队列名、索引前缀和模型名称必须来源于配置或集中常量，禁止在多个文件中重复硬编码。
- 检索、索引和缓存入库内容必须做长度截断和敏感信息过滤；维度不一致、JSON 解析失败、缓存短暂异常必须可降级处理并记录可追踪日志。
- 后台 worker 必须保证单条消息失败不阻断整个消费循环；消息确认、重试、死信或失败回投策略必须明确，禁止吞掉异常后让任务永久静默丢失。
- 内部接口必须校验内部凭证或等价认证机制；禁止因为内网调用就跳过身份校验和输入校验。
- 用户输入、正文内容、提示词、搜索词和模型输出都视为不可信数据；写入缓存、对象存储、数据库、日志或返回前必须做长度限制和必要清洗。
- 生成式 AI 输出不得直接作为权限、审核、资源状态或账号状态的最终事实来源；涉及业务结果变更时必须保留规则校验、人工可追踪依据或后端最终确认。
- 日志统一使用 `logging.getLogger(__name__)`；禁止使用 `print` 输出运行日志，禁止记录明文密钥、JWT、验证码、完整手机号、完整邮箱和完整用户私密文本。
- 捕获异常时必须区分可降级异常和系统错误；禁止大范围 `except Exception` 后直接返回成功，必须至少记录上下文并返回明确失败响应或降级结果。
- 文件、图片、视频和 HTML 处理必须限制大小、类型和来源；禁止信任用户提供的 URL 直接无限制下载或转发。
- 新增第三方依赖必须写入依赖清单并说明用途；禁止为了少量逻辑引入重量级依赖或与现有运行模型冲突的框架。
- Python 代码格式应保持 Black / Ruff 友好的换行与导入顺序；禁止一行多个语句、超长链式调用和为压缩行数牺牲可读性。
- 新增核心逻辑应补充可独立运行的单元测试或最小验证脚本；涉及外部服务时必须可通过 mock、假客户端或配置开关验证失败分支。

## 13. 测试与验收纪律

- 每次修改必须评估对认证、授权、核心流程、状态流转、通知和审计链路的回归风险。
- 新增核心业务不能只依赖应用启动测试，必须补充与风险匹配的自动化测试。
- 权限、状态机、事务、并发、幂等、逻辑删除、唯一约束和历史兼容属于重点测试范围。
- 修复缺陷时应尽量增加能够复现问题的测试。
- 后端修改后至少运行相关 Maven 测试。
- 前端修改后至少运行生产构建检查。
- Python 服务修改后至少运行相关单元测试、导入检查或最小启动检查。
- 涉及数据库迁移、MySQL、Redis、消息队列、对象存储或并发行为时，应执行相应集成验证；无法执行时必须明确说明。
- 完成任务前必须对照当前阶段验收标准复核，不能只确认代码能够编译。

## 14. Codex 工作要求

- 开始任务前先阅读本文件和当前阶段需求文档。
